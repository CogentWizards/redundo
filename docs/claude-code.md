# Adapter spec: Claude Code native OTLP telemetry -> the redundo.analyzer Event schema

This is the contract this adapter implements. Everything here was verified
against real captured telemetry from a running Claude Code session (CLI
`-p` mode, version 2.1.131), not derived from Anthropic's published docs
alone -- several of the decisions below exist specifically because the
docs and the actual emitted data disagree, and the code follows what was
observed. Where that's the case it's called out explicitly.

## Two signals, not one

Claude Code splits telemetry across two independent OTLP exports:

- **traces** (`/v1/traces`, `OTEL_TRACES_EXPORTER=otlp`): the span tree.
  Session grouping, parent/child structure, timing, token counts.
- **logs** (`/v1/logs`, `OTEL_LOGS_EXPORTER=otlp`): structured events.
  Most importantly `claude_code.tool_result`, which is the *only* place
  MCP tool call arguments appear, at any logging level, on any signal.

Traces alone still produce a valid corpus -- every record the schema
requires is still emitted -- but MCP tool calls degrade to opaque content
(never match anything, see below) without the logs signal too. This
adapter's `convert()` accepts a mix of both document types and is
tolerant of receiving only one.

## task_id

`session.id`, present as an attribute on every span (confirmed: this
adapter has never observed a Claude Code span without it, in traces
generated by the CLI). No fallback ambiguity like OpenInference's
`gen_ai.conversation.id` scattered-attribute problem -- Claude Code
attaches it uniformly.

If a span genuinely lacks it (a source anomaly, or
`OTEL_METRICS_INCLUDE_SESSION_ID` set falsy, which the docs describe as a
metrics-only cardinality control but may bleed into traces on some
configuration), the adapter falls back to that span's own trace ID, and
records `metadata.task_id_source = "trace_id_fallback"` instead of
`"session_id"` -- same "never synthesize, always report which happened"
discipline as `redundo.adapter.sources.openinference`.

**A session spans many separate OTLP traces.** Each user turn
(`claude_code.interaction`) is its own trace with no real parent link to
the previous turn's trace -- there is no TRACEPARENT propagation between
turns in normal CLI usage. Grouping by `session.id` rather than trace ID
is what makes cross-turn redundancy (e.g. re-reading a file two turns
after the first read) detectable at all.

## Lineage: real structure plus a session-wide linear bridge

Claude Code's real span hierarchy is shallow and well-documented:
`claude_code.interaction` (never kept -- see below) is the direct real
parent of every `claude_code.llm_request` and `claude_code.tool` span in
that turn. Subagent spans (via the Agent/Task tool) nest one level deeper,
under the parent `claude_code.tool` span.

Two things follow from this that aren't obvious from the span names alone:

1. **The ancestor key is the span's raw `parent_span_id`, not "the nearest
   kept ancestor."** `claude_code.interaction` is a structural span (see
   below) and is *never itself converted into a record* -- but spans that
   share it as their real parent are still real siblings that should
   chain to each other in start-time order, exactly like the linear
   fallback `redundo.analyzer.lineage` already applies when a source sets no
   `parent_id` at all. Walking *past* the interaction span looking for
   something "kept" (the strategy `redundo.adapter.sources.openinference` uses, correctly,
   for OpenInference's deeper AGENT-kind nesting) would make every direct
   child of `claude_code.interaction` an isolated root -- confirmed as a
   real bug during development, not a hypothetical.

2. **Chaining is unconditional start-time order, not interval-overlap
   detection.** `redundo.adapter.sources.openinference`'s adapter treats two same-ancestor
   siblings as concurrent (don't chain) when their `[start, end]`
   intervals genuinely overlap. That heuristic is *actively wrong* for
   Claude Code: a `claude_code.llm_request` span's own recorded end time
   is later than the start time of the tool calls it triggers, confirmed
   directly from real captured timestamps (the tool call begins while the
   model's request span is still "open," presumably because the span
   doesn't close until the full response including all tool_use blocks
   has been processed). Interval-overlap detection would read this --
   the *normal* relationship between essentially every llm_request and
   the tool call(s) it produces -- as concurrent branching, and refuse to
   chain almost everything. This adapter chains purely by start-time order
   among same-ancestor siblings instead. The tradeoff: a source that truly
   does run multiple tool calls in parallel within one turn will have them
   chained sequentially rather than recognized as fan-out. Given Claude
   Code's CLI is single-threaded except for subagent delegation (which
   nests at a different level and is unaffected by this), this is judged
   an acceptable v1 tradeoff, not an oversight.

`step_index` is assigned once, globally, per session (not reset per
interaction/trace) -- this is what lets the second trace's root event
(`parent_id = None`, since it has no real ancestor of its own) get bridged
to the first trace's last event by `redundo.analyzer.lineage`'s own,
already-established linear fallback. No adapter-side cross-trace stitching
is implemented or needed.

## Span kinds

Kept (converted into records): `claude_code.llm_request` ->
`llm_call`; `claude_code.tool` -> a synthetic `(tool_call, tool_result)`
pair (see below -- Claude Code represents an entire call+result as one
span, unlike OpenInference's separate TOOL spans).

Structural (read for metadata, never emitted as their own record):
`claude_code.interaction` (source of `user_prompt`), `claude_code.tool.execution`
(source of the call's outcome), `claude_code.tool.blocked_on_user` (fallback
outcome source when execution never started -- a rejected permission
decision).

Anything else (`claude_code.hook`, and any future span name) is counted in
`ConversionSummary.skipped_by_kind`, never silently dropped without a
trace in the summary.

## Splitting `claude_code.tool` into call + result

- **Outcome**: read from the child `claude_code.tool.execution` span's
  `success` attribute. If execution never started (blocked and rejected),
  falls back to the child `claude_code.tool.blocked_on_user` span's
  `decision` attribute (`"reject"` -> `error`).
- **Call content** (for `content_hash`), in preference order:
  1. The logs-joined `tool_result` record's `tool_input` field (full JSON
     arguments) -- works for every tool, including MCP ones, and is the
     *only* source of arguments for MCP tools (see below).
  2. The span's own `OTEL_LOG_TOOL_DETAILS`-gated attributes (`file_path`,
     `full_command`, `skill_name`, `subagent_type`) -- covers Claude
     Code's built-in tools when the logs signal isn't captured.
  3. Neither present -> an opaque hash (see "Opaque content" below).
- **Result content**: the `tool.output` **span event** (a nested,
  timestamped record inside the span -- not an attribute; populated by
  `OTEL_LOG_TOOL_CONTENT=1`, requires tracing enabled). This is the *only*
  place output content ever appears, for any tool, on any signal --
  confirmed empirically, including for MCP tools (the logs-joined
  `tool_result` record carries `tool_result_size_bytes`, a byte count,
  never the actual output). **If this event is absent, no `tool_result`
  record is emitted at all** -- see "Opaque content" for why a fabricated
  result hash would be actively unsafe here, unlike for a call or an
  llm_call.

## MCP tool argument join: positional, not by ID

Published docs describe `tool_use_id` / `gen_ai.tool.call.id` as present
on `claude_code.tool` (and its child `claude_code.tool.execution`) spans.
**Empirically, as of Claude Code 2.1.131, neither ID appears on any span
of either kind, under any combination of the documented logging flags.**
The only place `tool_use_id` reliably appears is on the *logs* signal's
`tool_result` record.

Without a span-side ID, this adapter joins the Nth `claude_code.tool` span
(by start time) within a session to the Nth `claude_code.tool_result` log
record (by `event.sequence`, a monotonic per-session counter across every
log record type) in that same session, and cross-checks `tool_name` before
trusting the pairing (accounting for the MCP naming split: the span
usually carries the fully-qualified `mcp__server__tool` name directly,
while the log record's `tool_name` is always the generic `"mcp_tool"`
marker, with the real names in a separate `tool_parameters` field). A
mismatch means the positional assumption broke -- most likely genuine
parallel tool dispatch within one turn reordering one signal relative to
the other -- and the adapter falls back to no join rather than risk
attributing the wrong arguments to a call. `ConversionSummary` reports
`mcp_tool_calls_total` / `mcp_tool_calls_with_arguments` so this degradation
is visible, not silent.

If a future Claude Code version adds the documented `tool_use_id` to
spans, this adapter should be updated to prefer an ID-based join (reliable
under reordering) and use the positional strategy only as a fallback.

## `llm_call` content: only the first completion per turn is hashable

`claude_code.llm_request` spans carry no prompt or response text under
any flag combination, on either signal -- confirmed empirically, not
assumed. The only prompt text anywhere is the *interaction's* own
`user_prompt` attribute (gated by `OTEL_LOG_USER_PROMPTS=1`; the sentinel
value `"<REDACTED>"` when unset is detected and never used as content --
hashing it as-is would make every session's first prompt look identical).

Every `llm_request` within one turn shares the *same* direct parent (the
interaction span) -- they are not nested progressively round-to-round.
Only the earliest one (by start time) under a given interaction actually
responds to that interaction's `user_prompt`; later completions in the
same tool-use loop (after tool results come back) have no prompt text
available at all. The adapter tracks this explicitly (the first
`llm_request` per interaction, computed once before the main conversion
pass) rather than checking "is my direct parent the interaction span,"
which is true for all of them and would give every round of a multi-round
tool loop the same, wrong, content_hash.

## Recovering `llm_call` content when there's no interaction span at all

The above assumes a `claude_code.interaction` span exists to hang the
`user_prompt` attribute on. It doesn't, for sessions captured through the
**Claude Agent SDK**: confirmed by reading the SDK's own
`_build_command()` (`claude_agent_sdk/_internal/transport/subprocess_cli.py`),
every `query()` call launches the CLI with `--input-format stream-json
--output-format stream-json`, and confirmed against a real captured
`claude_agent_sdk.query()` run, that code path never constructs the
interaction span at all -- not a dropped-but-referenced one, a genuinely
absent one, with `llm_request`/`tool` spans carrying no `parent_span_id`
whatsoever. Without this fix, every `llm_call` from such a session got an
opaque hash, unconditionally -- even though the *logs* signal's
`user_prompt` event (session-level, `event.sequence`-ordered, same
`<REDACTED>` sentinel handling) is still present and populated in this
same capture mode. The gap wasn't missing data; it was a missing way to
join two things that were both right there.

### Why an ID join isn't possible here

Every other cross-signal join in this adapter uses an exact ID:
`request_id` for cost (`_index_api_request_logs`), a positional-plus-
tool-name-cross-check for MCP arguments (`_index_tool_result_logs_by_session`).
Both exist because *something* survives on both sides to match on. Here,
nothing does: `claude_code.llm_request` carries no `prompt.id`, in either
capture mode, at any logging level -- confirmed by inspecting every
attribute Claude Code puts on that span (see "Standard Span Attributes"
and the `llm_request`-specific table in Anthropic's own monitoring
reference; `prompt.id` is documented as a *logs-signal-only* correlator).
So this can't be an ID join. It has to be inferred from the one thing
both signals reliably share: real wall-clock time.

### The mechanism: time-window bucketing (`_resolve_windowed_prompts`)

1. **Build turn windows from the logs signal.** Sort the session's
   `claude_code.user_prompt` log records chronologically (`event.sequence`,
   same tie-breaking as every other logs-side sort in this adapter). Each
   record's `event.timestamp` (parsed to nanoseconds by `_parse_iso_to_nano`
   -- ISO 8601, handling both a trailing `Z` and an explicit `+00:00`
   offset, since real captures show both) marks the start of a window that
   runs until the *next* `user_prompt` record's timestamp, or to
   `+infinity` for the last one. A record whose prompt is missing, empty,
   or the `<REDACTED>` sentinel contributes no window at all -- same
   discipline as the interaction-span path, just applied per log record
   instead of per span.
2. **Assign each `llm_request` span to a window by real start time.**
   Sort the session's kept `llm_request` spans by `start_time_unix_nano`.
   For each one with `parent_span_id is None` (the Agent SDK signature --
   a span *with* real parent info always uses the precise path instead,
   see below), find the window whose `[start, end)` contains that span's
   own start time.
3. **Only the first span to land in a window wins it** -- the exact same
   "first completion of a turn" rule as the interaction-span path, just
   enforced with a `claimed_windows` set instead of `claimed_interactions`.
   A second, third, etc. `llm_request` in the same window (a multi-round
   tool-use loop within one Agent SDK turn) correctly falls through to
   opaque, unchanged from before.
4. **The result is a `{span_id: prompt text}` map**, resolved once per
   session before the main per-span conversion loop (mirroring
   `first_llm_request_of_interaction`'s own pre-pass), then consulted by
   `_llm_event()` as a fallback *only* when the precise interaction-span
   path found nothing for that span. A record that used it carries
   `metadata.content_basis = "prompt_windowed"` -- deliberately distinct
   from plain `"prompt"`, so a report reader (or this adapter's own
   `ConversionSummary.notes()`) can tell a heuristic recovery from an
   exact one, the same way `"tool_input"` vs `"opaque"` already
   distinguishes provenance elsewhere.

### The safety gate: never touches a session that has a real interaction span

`_resolve_windowed_prompts()` is only ever *called* when
`_convert_session()` has already confirmed zero `claude_code.interaction`
spans exist anywhere in that session -- not per-span, per-session. This
matters because direct CLI sessions can *also* contain an orphan
`llm_request` with `parent_span_id=None` sitting alongside otherwise-normal
interaction spans (observed early in this project's own research: a
session-title-generation call, `query_source="generate_session_title"`,
issued outside the interaction tree). If the time-window heuristic ran
unconditionally on every parentless span, that orphan call would
incorrectly inherit whatever turn's window it happened to fall inside --
a wrong, confident-looking match, not an honest "couldn't tell." Gating on
the whole session is what prevents that: a session with real interaction
spans never computes windows at all, so the precise path and the
heuristic path can never collide or produce a false match against each
other. `test_windowed_fallback_never_fires_when_interaction_span_present`
verifies this directly, with a decoy window positioned so it *would*
match the orphan span if the gate were missing.

### What this doesn't fix, and why

- **Precision is inherently looser than the ID-based joins.** Two signals
  exported on independent schedules (`OTEL_TRACES_EXPORT_INTERVAL` and
  `OTEL_LOGS_EXPORT_INTERVAL` are separate settings) means real clock
  skew between when a `user_prompt` event's timestamp was recorded and
  when the corresponding `llm_request` span's was is possible, though the
  causal ordering (prompt necessarily precedes the response that answers
  it) should hold in practice.
- **A session with no `user_prompt` log records at all** (traces
  captured without `OTEL_LOGS_EXPORTER=otlp`, or without
  `OTEL_LOG_USER_PROMPTS=1`) has no windows to build and degrades to
  opaque, exactly as before this fix -- `_resolve_windowed_prompts()`
  simply isn't called.
- **Genuinely concurrent turns** (if the Agent SDK is ever driven to
  process two prompts whose processing windows overlap in real time --
  not observed, and not how `query()`'s documented usage works) would
  break the non-overlapping-windows assumption. Not something this
  adapter can detect from the data available; a wrong-but-plausible match
  is the realistic failure mode there, same caveat the MCP positional
  join already carries for true parallel tool calls.

## Opaque content: safe for calls, unsafe for results

When there's no real content to hash, an `llm_call` or `tool_call` record
still gets emitted -- with a content_hash derived from the span's own
`span_id` (unique by construction, so it can never coincidentally collide
with another record's hash). This preserves the record's contribution to
token/cost/coverage accounting (central to "where did my tokens go")
while making it structurally inert for candidate-pair matching: it can
never look like a false repeat.

**This trick is deliberately not applied to `tool_result` content.**
`classify.py`'s `_result_signal()` treats an *unequal* hash as positive
evidence the result changed (`LEGIT_SUPPORTING`), not as "unknown." A
per-span opaque hash would therefore manufacture a false "result changed"
claim on every unobservable-result pair; a constant sentinel hash would
manufacture the opposite false claim ("result identical," which can feed
`confirmed_waste`). The only representation of "unknown result" this
schema actually has is the one `redundo.adapter.sources.openinference` already
established: no `tool_result` event at all, so `_correlated_result_hash()`
finds nothing and reports `Signal.UNKNOWN` honestly. See
`convert.py::_tool_events()`'s comment for the full reasoning -- this was
a real bug caught during development, not a hypothetical avoided in
advance.

Every record's `metadata.content_basis` names which case applied
(`"prompt"`, `"tool_input"`, or `"opaque"`), so "zero repeats because
nothing repeated" and "zero repeats because nothing was observable" don't
look identical downstream -- same discipline as `redundo.adapter.sources.openinference`'s
`masked_spans` tracking.

## Cost: joined from the logs signal by `request_id`

`cost_usd` is never present on the `claude_code.llm_request` trace span.
It is present on the logs signal's `claude_code.api_request` record,
joined back to its span via `request_id` -- Anthropic's own per-call
request identifier, confirmed to carry the identical value on both
signals (unlike `tool_use_id`, which does not appear on the trace side at
all). `tokens_in` sums `input_tokens + cache_read_tokens +
cache_creation_tokens` from the span directly (all three are genuinely
separate token pools in the underlying Messages API usage object, not
overlapping counts) -- `cost_usd` is used as-provided, never computed from
a price table, consistent with `redundo.adapter.sources.openinference`'s "no price table"
design.

## `metadata.write` is never set

No signal indicates whether a tool call mutated anything. Inferring it
from `tool_name` (`"Bash"` could be `ls` or `rm -rf`) would be a guess
dressed as a finding. This leaves tool_call write status
`Signal.UNKNOWN` for every record from this adapter, which is the correct,
conservative default the schema already documents.

## Known gaps, stated plainly

- **MCP tool call *results* are never observable**, on any signal, at any
  logging level. Every MCP `tool_call` this adapter emits will have no
  paired `tool_result` unless a future Claude Code version starts emitting
  `tool.output` events for MCP tools too.
- **`tool.output`'s content attribute key varies per tool.** Confirmed
  empirically, not documented anywhere: Read uses `content`, Bash uses
  `output`. `_tool_result_content()` checks both (`_TOOL_OUTPUT_CONTENT_KEYS`);
  other built-in tools (Edit, Write, Grep, Glob, ...) haven't been directly
  observed and may use a third key, in which case they correctly degrade
  to "no result" rather than risk picking up the wrong field under a
  guessed name.
- **Claude Agent SDK sessions have no `claude_code.interaction` span at
  all** (confirmed against a real captured `claude_agent_sdk.query()` run
  -- the SDK always launches the CLI in streaming mode, which never
  constructs it). Lineage is unaffected -- `redundo.analyzer.lineage`'s own
  linear fallback bridges parentless spans correctly regardless.
  `llm_call` content recovery for this case is handled by a dedicated
  time-window correlation against the logs signal; see "Recovering
  `llm_call` content when there's no interaction span at all" above for
  the full mechanism, its safety gate, and what it still can't fix.
- **`llm_call` content matching is limited to the first completion of each
  turn.** A model re-generating a similar completion mid-tool-loop is
  invisible to candidate-pair detection; it's still visible in cost/token
  totals (see "Opaque content" above).
- **Read/Edit/Grep argument precision**: `file_path` alone (the only
  argument Claude Code exposes for these tools) doesn't distinguish two
  different `offset`/`limit` reads of the same file, or two different
  edits to the same file -- both would show as candidate-identical calls
  when they may not be. `OTEL_LOG_TOOL_CONTENT`'s `tool.output` event
  content (the actual returned text) still lets `_result_signal()` tell
  them apart in practice for Read; Edit's arguments have no such
  fallback.
- **Flush-on-exit risk for short sessions.** Claude Code's own docs
  acknowledge spans can be dropped if the process exits before its batch
  exporter flushes; confirmed directly (the `claude_code.interaction` root
  span was silently missing from an early capture at the default 5-second
  export interval). Set `OTEL_TRACES_EXPORT_INTERVAL=1000` (or lower) --
  this measurably fixed it in testing, though Anthropic's own docs still
  describe the flush as "bounded by a short timeout," so it isn't a hard
  guarantee for very short-lived invocations.
- **Version-dependent.** Several of the decisions above (no `tool_use_id`
  on spans, no `trace_id`/`span_id` on log records) reflect Claude Code
  2.1.131's actual behavior, not necessarily its published spec or future
  versions. If a newer version starts emitting these fields, the
  positional-join fallback and its cross-checks remain correct (a
  reliable ID join is a strict improvement, not a breaking change), but
  should be preferred when available.

## Recommended setup

```bash
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1
export OTEL_TRACES_EXPORTER=otlp
export OTEL_LOGS_EXPORTER=otlp
export OTEL_METRICS_EXPORTER=none   # not consumed by this adapter
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
export OTEL_TRACES_EXPORT_INTERVAL=1000
export OTEL_LOGS_EXPORT_INTERVAL=1000
export OTEL_LOG_USER_PROMPTS=1      # first-of-turn llm_call content
export OTEL_LOG_TOOL_DETAILS=1      # built-in tool arguments + MCP tool_input
export OTEL_LOG_TOOL_CONTENT=1      # tool.output content (needs tracing on)
```

Then, in a separate terminal, run `redundo collect --out-dir
./otlp_traces` before starting any `claude` session (see the top-level
README for what this collector is and when you'd point at a different one
instead), and convert what it captures:

```bash
redundo adapt ./otlp_traces -o trace.jsonl --summary
redundo analyze trace.jsonl --format html --output report.html
```
